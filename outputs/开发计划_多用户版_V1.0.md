## 0. AI 协作开发特别约定

### 0.1 上下文管理
- **每次开工前必读**：本文件 + 《PRD_多用户版_V1.0.md》+ 当前任务对应的单用户版 PRD 章节（如需要）；
- **上下文压缩策略**：AI 工具上下文有限，优先粘贴"任务描述 + 验收标准 + 相关代码文件路径"，而非全仓代码；
- **关键文件锚点**：在任务描述中明确写出需要修改的文件路径，减少 AI 自主探索的偏差。

### 0.2 代码一致性
- **命名约定**：多用户相关变量统一用 `user_id`（不是 `uid` / `owner_id` / `account_id`）；
- **查询过滤**：所有 SQLAlchemy 查询必须显式 `.filter(Model.user_id == current_user_id)`，禁止依赖"默认查询全部"；
- **API 设计**：管理员查看其他用户数据时，URL 显式带 `?user_id=` 参数，禁止隐式切换。

### 0.3 验证门禁（AI 易绕过，必须强制执行）
- **每任务完成后**：`pytest` 通过 + `oxlint` 0 error + 新增代码覆盖率 ≥ 85%；
- **数据库迁移**：必须在真实 PostgreSQL 上重放（CI 已有 `test_alembic_postgres.py`，新增多用户迁移测试用例）；
- **权限测试**：每个涉及数据访问的任务，必须包含"用户 A 不能访问用户 B 数据"的测试用例。
- **⛔ 合并红线（最高优先级，任何任务不得违反）**：
  1. **M2-5（含全局隔离测试）未完成前，multiuser-v2 分支禁止部署到生产、禁止合并 main**——此前系统处于"多用户表结构 + 单用户数据访问语义"的中间态，多用户场景下必然串数据；
  2. **M1-4 存量数据回填未在生产/演练库执行前，禁止合并**——中间态下新写入的行 user_id 为空，回填脚本漏一行即永久丢数据；
  3. 违反红线的合并视为事故，回滚后重新走流程。

### 0.4 防范围蔓延
- AI 容易"顺手优化"无关代码，任务描述中明确写"**仅修改以下文件，不要动其他文件**"；
- 发现 PRD 未覆盖的场景，先记录到 TECH_DEBT.md，不擅自扩展实现。

## 关键风险与应对

| 风险 | 概率 | 影响 | 应对 |
|------|------|------|------|
| AI 生成的权限过滤遗漏某个查询 | 中 | 数据泄露 | M2-5 强制"每处修改附带权限测试用例" + **全局隔离测试遍历全部端点**；人工 code review 时 grep `user_id` |
| 中间态（表结构已多用户、数据访问未隔离）被提前部署/合并 | 中 | 数据泄露 + 回填漏行丢数据 | §0.3 与 M-M6 的合并红线；M2-5 完成前禁止部署/合并 |
| 多用户后 HTTP 明文导致凭据泄露 | 高（若不上 HTTPS） | 密码/佳明凭据/LLM Key 泄露 | M6-4 强制：邀请任何用户前必须上 HTTPS 或 Tailscale；域名备案周期长，M-M1 开工时即启动申请 |
| 佳明 429 在多用户下更频繁 | 高 | 同步失败 | 串行同步 + 每用户独立退避；监控 job_run 失败率 |
| 迁移脚本破坏存量数据 | 低 | 数据丢失 | M1-4 强制 `--dry-run`；M6-2 演练；备份先行 |
| AI 过度发挥引入未要求的功能 | 中 | 范围蔓延 | 任务描述明确"仅修改以下文件"；完成后 diff review |
