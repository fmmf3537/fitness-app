## 二、审计发现明细

### P1 — 建议近期处理（3 项）

#### P1-1 生产备份双轨不一致：compose 备份容器与应用内备份服务并存且后者在 PG 下静默跳过
- **位置**：`backend/app/services/backup.py`（L70-73：非 SQLite 时 `status=skipped`）vs `docker-compose.yml`（`backup` 服务 pg_dump）vs `scheduler.py`（每日 03:17 注册 `db_backup_daily`）。
- **问题**：生产（PostgreSQL）环境下，应用内每日备份任务每天跑、每天 skipped、每天写一行 `job_run`，形成"永久 skipped 噪音"，会掩盖真正的失败告警模式；同时 `deploy/backup` 容器的 pg_dump 才是真实备份来源，但两条路径从未在文档中声明"谁为准"。
- **建议**：二选一并在 `docs/DEPLOY.md` 写明。推荐保留 compose pg_dump 容器，应用内 `backup_fn` 在检测到非 SQLite 时**不注册** cron job（而非跑了再 skipped），消除噪音。

#### P1-2 本地备份目录断档 11 天，与"每日备份"承诺不符
- **位置**：`backend/data/backups/` 仅有 `app_2026-08-10.db`（274MB）一个文件；当前日期 2026-08-21。
- **问题**：开发机上的每日 03:17 备份任务自 08-10 后无产出（很可能本机服务未常驻，见下条）。SQLite 单文件 274MB 且包含全部历史训练/健康数据，**当前唯一副本就是工作库本身**，一旦误删/损坏不可恢复。
- **建议**：本机开发期也应有保底备份策略（哪怕每周一次手动 `cp` 或 Windows 任务计划）；或明确接受"本机数据可随时由训记+佳明重新回填"并在文档中声明该前提成立（注意：AI 报告、追问记录、手动录入的身体数据**无法**从外部回填，这部分是真实单点）。

#### P1-3 `logs/backend.log` 显示服务曾异常退出且端口冲突反复出现
- **位置**：`logs/backend.log` 末尾：`[Errno 10048] error while attempting to bind on address ('127.0.0.1', 8000)`，前一段还有 PowerShell 包装脚本异常输出混入日志。
- **问题**：印证了 TECH_DEBT T11（"定时任务未做 7 天无人值守实测"）仍然开着——本机常驻进程的可靠性（端口占用、异常退出后无 supervisor 拉起）是已知但未闭环的风险。APScheduler 的 MemoryJobStore 意味着进程一死，当日 22:47 同步就静默缺席。
- **建议**：三选一——(a) 用 Windows 任务计划/NSSM 托管 uvicorn 实现退出自启；(b) 接受缺席，但给 `daily_sync` 加"上次成功运行距今 >36h 则启动时补跑"的启动补偿逻辑；(c) 尽快推进 V2-5 上云（compose `restart: unless-stopped` 天然解决）。

### P2 — 机会项（5 项）

1. **`GARMIN_BACKFILL_START_DATE` 死代码**（T16 已登记，仍未清理）：`config.py` 定义了默认值 `2017-01-01`，compose 也注入了该变量，但全仓无引用。要么删除，要么在佳明活动分页拉取处真正接入起始日期过滤。
2. **`backend/backend/` 目录疑为误建**：`backend/` 下存在一个同名子目录 `backend/backend/`（8-04 创建），建议确认内容后删除，避免与包路径混淆。
3. **截图确认入库服务端幂等**（T23 已登记，保留中）：当前靠前端按钮置灰兜底。鉴于 `xunji_train` 有 `UNIQUE(datestr, localid)` 约束兜底、且 localid 带 `shot-` 前缀可追踪，风险确属低，维持现状可接受，但补一个 `client_request_id` 去重成本很低。
4. **依赖版本全部使用下界约束（`>=`）**：`requirements.txt` 未锁定上界，`garth>=0.8` 尤其值得注意——garth 已宣布停维护（T1），未来某次 `pip install` 可能拉到破坏性新版。建议至少对 garth、apscheduler、fastapi 锁定兼容上界，或生成 `requirements.lock`（pip freeze）供 Docker 构建使用。前端 `package-lock.json` 已锁定，无此问题。
5. **`frontend/android/` 目录体量与维护策略未见说明**：Capacitor 安卓工程已入库（PRD 写"Tauri 套壳 V2，非 MVP"，实际选了 Capacitor，属已闭环的文档偏差，但 PRD §2「桌面端」一行未同步更新）。建议下次修订 PRD 时把移动端栈正式写进去。

## 三、亮点（值得保持的做法）

- **密钥纪律**：全仓 grep 复核无硬编码密钥；`.env`、素材 Key 文件、日志、数据库均被 gitignore；git 追踪文件中仅 `.env.example` / `.env.production.example` 模板与 1 个测试 fixture。✅
- **认证覆盖**：15 个 API 路由文件全部挂 `Depends(require_auth)`（workouts/backfill/sync/screenshot 等逐一核实）；登录用 `secrets.compare_digest` 防时序攻击；生产模式缺 `APP_PASSWORD`/`FERNET_KEY` 或非 PG 直接拒绝启动。✅
- **写回安全**：全仓仅两处 `dry_run=False`（确认流 + 身体数据 confirmed 流），未确认时抛错且不外呼；训记所有请求收敛于单一限频装饰器。✅
- **网络安全**：生产链路 backend 不暴露端口，经 frontend(nginx) 同源反代 → Caddy HTTPS（自动 LE 证书 + 安全响应头），无 CORS 面。✅
- **上传防护**：截图导入有数量（≤9）/单张体积（≤10MB）/MIME 白名单三重限制。✅
- **测试基建**：真实 API 集成测试全部走 `RUN_*_INTEGRATION=1` 显式门禁，CI 无凭据也能全绿；PG 迁移在 CI 用服务容器真实重放。✅
- **演进留痕**：87 次提交、8 个 sprint tag、TECH_DEBT 从 T1 跟踪到 T31，含 flake 根因分析（T29）和"小米导出格式三连坑"经验登记——这种密度在个人项目里非常罕见。
