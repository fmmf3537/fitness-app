# M1-4 存量数据迁移脚本 —— 开发提示词（待确认后由 Kimi Code CLI 执行）

> 通用前缀见《开发计划_多用户版_V1.0.md》§「给 AI 工具的通用前缀」。
> 本任务仅创建 `scripts/migrate_to_multiuser.py` 这一个文件及其单元测试，不要动其他文件（包括 models.py、迁移文件、业务代码）。

## 当前任务
新建 `backend/scripts/migrate_to_multiuser.py`：多用户化存量数据回填脚本。

## 背景（已确认上下文）
- `multiuser-v2` 分支已完成 M1-1（users/audit_log 表）、M1-2（settings 每用户一行）、M1-3（11 张业务表加 `user_id`）。
- 目前所有 `user_id` 列均为 **nullable**，存量记录 `user_id` 为 NULL。
- 本脚本把全部存量记录归属到「默认管理员」用户，使多用户结构可用。
- ⚠️ 此为破坏性回填脚本，**仅在 multiuser-v2 分支、且仅在用户明确要求执行时才真实写入**；默认提供 `--dry-run`。

## 功能要求
1. **默认管理员创建**：
   - 检查 `users` 表，若为空则创建默认管理员：
     - 用户名从环境变量 `ADMIN_USERNAME` 读取，默认 `"admin"`
     - 密码从环境变量 `ADMIN_PASSWORD` 读取；若该变量为空，则随机生成 16 位（含大小写字母+数字）密码，**仅打印一次到控制台**（明确提示用户保存）
     - `role = "admin"`，`is_active = True`
   - 若 `users` 表非空（已有管理员），则跳过创建，直接取第一个 admin（或按 `role='admin'` 排序取第一个）作为归属用户。
   - 返回管理员 `user_id`。

2. **存量记录的 user_id 回填**：为以下表的**所有 `user_id` 为 NULL 的记录**设置 `user_id = 管理员 id`：
   - `settings`、`xunji_train`、`garmin_activity`、`garmin_daily`、`body_metric`
   - `workout`、`match_candidate`、`xunji_plan`、`ai_report`、`llm_call`
   - `job_run`（注意：job_run 的 user_id 业务上可为 NULL 表示系统级任务，**仅回填当前 NULL 且属于业务数据的行**，若无法区分则全部赋值，并在报告里标注）、`report_chat_message`
   - **关键约束**（避免重复/冲突）：回填前先 `SELECT ... WHERE user_id IS NULL`，逐表 UPDATE；`settings` 表若有多行 NULL（同一用户多行），全部归属管理员即可（UNIQUE(user_id) 会禁止管理员有多行——**若 settings 现有多行 NULL，需先去重或合并到一行，再赋值 user_id**，避免违反唯一约束；若无法自动合并，打印警告并跳过 settings 的赋值、记录在报告里）。

3. **迁移报告**：每张表输出「待处理行数 → 实际更新行数」，最后打印汇总（总表名、总行数、耗时）。

4. **`--dry-run` 参数**：仅输出「计划：每张表 X 行将被更新」，不执行任何 UPDATE。默认行为即为 dry-run，**必须显式传入 `--apply` 才真正写入**。

## 技术约束（非常重要）
- **不要 import `app.models` / `app.db`**，直接用 `sqlalchemy` 读 `DATABASE_URL`（从环境变量或 `.env` 解析，复用项目中已有的 `resolve_database_url` 逻辑思路：优先 `os.environ["DATABASE_URL"]`，否则读 `.env`），建立原生 `Engine` 与 `Connection`（或 `Session`），避免与 app 包循环导入。
- 数据库连接失败、表不存在等情况要有明确报错，不静默吞异常。
- 使用参数化 UPDATE（`text("UPDATE <table> SET user_id=:uid WHERE user_id IS NULL")`），禁止字符串拼接表名外的任何 id 值。
- 脚本顶部写清楚用法：
  - `python scripts/migrate_to_multiuser.py --dry-run` （查看计划，默认）
  - `python scripts/migrate_to_multiuser.py --apply` （真实写入；执行前必须先备份数据库）

## 测试要求
- 新建 `backend/tests/test_migrate_to_multiuser.py`（或在 `scripts/` 同级加 `tests/` 测试）：
  - 用临时 SQLite 库（建最小表结构：users + 上面 11 张表的 user_id 列），验证：
    1. dry-run 不修改任何行，但报告正确的待处理行数；
    2. 空 users 表时 `--apply` 创建管理员并回填，所有表 user_id 均等于管理员 id；
    3. 已存在管理员时，不重复创建，仍正确回填。
- 运行 `pytest tests/test_migrate_to_multiuser.py` 通过。

## 验收标准
1. 脚本可正常运行，`--dry-run` 输出正确的迁移计划（每张表行数）。
2. `--apply` 真实执行后，所有目标表 `user_id` 正确赋值，且**数据行数不变**（仅改 user_id，无增删）。
3. `pytest` 通过。
4. 不修改 models.py、迁移文件、业务代码——仅新增脚本与测试。

## 红线（必须遵守）
- **绝不**删除、清空任何表；仅 UPDATE `user_id`。
- 不改动除新增文件之外的任何文件。
- 真实写入（`--apply`）前在脚本内打印醒目警告，并要求 `--apply` 显式确认。
