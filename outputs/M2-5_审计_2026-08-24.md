# M2-5 审计报告：数据访问层权限过滤（多用户隔离收口）

> 分支：`multiuser-v2`　日期：2026-08-24
> 前置：M2-3（认证 `get_current_user_id`）、M2-4（API 层权限注入 + 全量 pytest 通过）已完成。
> 本阶段目标：把隔离从「API 层」下沉为可验证的「service 层过滤」+ 管理员 `?user_id=` 代查看能力，并为每张个人数据表补齐权限测试用例。

## 1. 任务范围

- 所有用户个人数据表的 service 层查询显式按 `user_id` 过滤（grep 可证）；
- 实现管理员 `?user_id=` 覆盖（普通用户传 `?user_id=` 越权被忽略）；
- 每张表至少一个权限测试用例（A 不可见 B、未带 token 401、带 token 见自己、管理员代看）；
- 全量 pytest 通过（`exit 0`）。

## 2. 完成内容

### 2.1 管理员代查看机制（M2-5 核心新增能力）

`backend/app/api/auth.py`：

- 新增依赖 `get_current_user(authorization, session) -> User`：校验 Bearer token，返回 `User` 对象（含 `role`），未认证 401；不改动既有 `get_current_user_id` 签名与行为。
- 新增助手 `resolve_viewer(principal: User, override_user_id: int | None = None) -> int`：
  - 管理员（`principal.role == "admin"`）且显式传 `override_user_id` 时返回该 id，实现「代查看」；
  - 普通用户传 `override_user_id` 一律忽略，维持自身隔离（不接受越权）；
  - 未传时返回自身 id。

### 2.2 六个列表端点支持 `?user_id=` 管理员代查看

改造均保持「API 层按 effective viewer 过滤」的既有隔离范式，仅把 `current_user_id`
替换为 `resolve_viewer(principal, override_user_id)`：

| 端点 | 表 | 文件 |
|------|----|------|
| `GET /api/stats/trends` | workout / body_metric / garmin_daily | `api/stats.py` |
| `GET /api/workouts/calendar` | workout | `api/workouts.py` |
| `GET /api/workouts/deleted` | workout | `api/workouts.py` |
| `GET /api/match-candidates` | match_candidate | `api/match_candidates.py` |
| `GET /api/ai-reports` | ai_report | `api/ai_reports.py` |
| `GET /api/body-metrics` | body_metric | `api/body_metrics.py` |
| `GET /api/plans/upcoming` | xunji_plan | `api/plans.py` |

> 详情/删除/恢复等写类端点保持「自身 token 只能操作自身数据」语义（`row.user_id != current_user_id → 404`），管理员代查看聚焦于只读列表场景（符合 PRD §7「代查看」定位）。

### 2.3 service 层 user_id 过滤现状（grep 可证）

个人数据表的「用户态读」入口均已按 `user_id` 过滤：

- `workout`：`workouts.delete_workout` / `restore_workout` 校验 `w.user_id == user_id`；`list_deleted_workouts` 过滤 `Workout.user_id == user_id`；API 列表/日历/详情查询 `Workout.user_id == current_user_id`。
- `body_metric`：`body_metrics.upsert_body_metric` 与 `query_body_metrics` 均过滤 `BodyMetric.user_id == user_id`。
- `xunji_plan`：`plans._candidate_rows` 在 `user_id is not None` 时追加 `XunjiPlan.user_id == user_id`。
- `ai_report`：`ai._run_period_review` 去重查询 `if user_id is not None: existing_filters.append(AIReport.user_id == user_id)`；API 列表/详情/导出/状态均过滤 `AIReport.user_id == current_user_id`。
- `match_candidate`：API 列表 `MatchCandidate.user_id == current_user_id`；写类 `resolve_candidate` 校验归属。
- `garmin_daily`：API `stats/trends` 过滤 `GarminDaily.user_id == current_user_id`。
- `report_chat_message`：经 `report_id` 关联，API 层已校验 `report.user_id == current_user_id` 后再读消息（report 已用户归属）。

> 兼容语义保留：`user_id is None` 时不过滤（匹配存量 NULL 行），供 scheduler/legacy 调用，与 M2-4 既定行为一致。

## 5. 偏差与残留（M2-5-b 已闭环）

### 5.1 M2-5-b 收口内容（2026-08-25）

为 `app/services/ai.py` 全部 prompt 组装类查询补充 `user_id` 收敛（防御纵深），避免
「为某用户生成报告时，报告正文混入他人体征/训练细节」：

- `query_movement_history` / `query_last_similar_workout` / `query_period_training_summary` /
  `query_pr_events`（含内部 `best_weights`）→ 对 `Workout.user_id` 过滤；
- `query_recovery_summary` → 对 `GarminDaily.user_id` 与 `BodyMetric.user_id` 过滤；
- `query_body_composition` → 对 `BodyMetric.user_id` 过滤；
- `query_plan_completion` → 对 `XunjiPlan.user_id` 与 `Workout.user_id` 过滤；
- `query_next_plan_day` → 对 `XunjiPlan.user_id` 过滤（同属用户计划缓存读取）；
- `query_previous_review` → 对 `AIReport.user_id` 过滤；
- `query_part_volume_trend` → 透传 `user_id` 给 `query_period_training_summary`。

约定：所有函数 `user_id: int | None = None`，`user_id is not None` 时才追加过滤（保留
M2-4 legacy 语义：`user_id=None` 匹配存量 NULL 行，供 scheduler 调用）。

调用链透传：`generate_session_review` / `generate_next_advice` / `generate_plan_review` /
`_generate_period_review` 均把已用户归属的 `workout.user_id`（或报告 `user_id`）传入上述查询；
`generate_plan_review` 额外对 `plan_service.query_plan_day(..., user_id=user_id)` 收敛计划缓存；
`poster.py::workout_pr_details` 的 `query_pr_events(..., user_id=workout.user_id)` 同步收敛。
