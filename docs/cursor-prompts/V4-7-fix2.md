## 审核发现的问题（审核方亲手跑 pytest 实测，唯一问题）

`backend/tests/test_set_hr.py::test_compute_workout_set_hr_end_to_end_idempotent` 仍失败：

```
assert r.hr_recovery_30s == 88 or r.hr_recovery_30s == 90
E  assert (100 == 88 or 100 == 90)   # 实际值为 100
```

**根因是夹具/断言设计缺陷，服务实现是正确的**：

- `_make_mini_raw`（第 304-338 行）的常规 HR 序列覆盖 0~154 秒每秒一点
  （hr = 100 + sec%5），**t=60000 处已存在常规点 hr=100**；
  末尾又注入 `(60000, 88)`、`(61000, 90)`（第 325-326 行），与常规点同刻撞车。
- 组 1 结束于 30000ms → 恢复目标 60000ms，窗口 [55000, 65000] 内
  `(60000,100)` 与 `(60000,88)` **距离同为 0 并列**；timeline 稳定排序后常规点在前，
  服务按提示词规范「取窗口内时间最接近目标的点」确定性选中 100。服务行为合规。
- 撞车的注入点使「88」的期望永远无法成立。且 `compute_recovery_hr` 的选取语义已有
  两个专项单测覆盖（均通过），e2e 只需断言确定性结果。
