**现状**：`.gitignore` 第 2 行只写了 `.env`，**精确匹配根目录 `.env` 本身**，不匹配 `.env.*` 变体。

`git check-ignore -v` 实测确认以下两个文件**未被忽略**，`git status` 已列为 `??` 未跟踪：

| 文件 | 暴露内容（已脱敏，仅列变量名） |

| `.env.multiuser-v2.bak` | `FERNET_KEY`、`POSTGRES_PASSWORD`、`APP_PASSWORD` |

**风险**：一次 `git add . && git push` 即全部泄露到 GitHub 公开/私有仓库。
`FERNET_KEY` 泄露尤其致命——它是加密存储的**主密钥**，拿到即可解密库里所有已加密凭据。

**已核实的好消息**：
- `git log --all` 确认这两个文件**从未进入任何提交**
- `git ls-tree -r origin/main` 确认远程只有 `.env.example` / `.env.production.example`，**远程干净**
- 两分支与 origin 差距均为 `0 0`，无待推送内容

**处置**：
1. `.gitignore` 改为 `.env.*`（并保留 `!.env.example`）
2. 两个文件移出工作区或删除
3. **轮转上述全部密钥**（尤其是 `FERNET_KEY`、`GARMIN_PASSWORD`、`APP_PASSWORD`）——文件存在过就不该假设未外泄

## 五、一个需要澄清的指标：匹配率不是 8.9%

初看 `workout.match_status` 分布会得出"匹配算法失败"的结论：

```
garmin_only 597 | xunji_only 65 | auto_matched 65 | 'x' 1   →  自动匹配仅 8.9%
```

**但这是分母错了**。核对两源数据覆盖：

| | 条数 | 时间覆盖 |
|---|---|---|
| xunji_train | 133 | 2023-02-09 ~ 2026-08-27 |
| garmin_activity | 662 | 2017-12-12 ~ 2026-08-26 |

佳明 662 条中有 **498 个日期训记根本没记录**（跑步/游泳等有氧只在佳明侧），
这 597 条 `garmin_only` 属**单源数据，不是匹配失败**。

正确的算法：

| 口径 | 结果 |
|---|---|
| **近 90 天**（PRD 验收口径） | **17/18 = 94.4%** ✅ 达标 |
| 训记侧全量 | 65/130 = 50.0% |

**结论**：近 90 天达标，无需返工。但全量 50% 意味着**历史段（2023–2026 早期）有约 65 条未配**，
建议抽样 10 条核查原因——可能是历史时间戳时区对齐问题，也可能是真实的单边训练，需确认后决定是否处理。

### 7.2 数据库 schema 污染：已知、良性、暂不处理

`backend/data/app.db` 仍残留多用户分支迁移的痕迹（这是当初在 `multiuser-v2` 分支跑迁移后切回 `main` 留下的）：

**4 张孤儿表**（`models.py` 无对应模型、Alembic 无对应迁移）

| 表 | 行数 | 说明 |
|---|---|---|
| `users` | 2 | admin(1)、alice(2)，alice 为测试用户 |
| `auth_token` | 0 | 空表 |
| `audit_log` | 1 | 一条测试日志 |
| `leaderboard_cache` | 0 | 空表 |

**4 个隐形 `user_id` 列**（ORM 不可见）

| 表 | 列定义 | 取值分布 |
|---|---|---|
| `workout` | nullable，无默认值 | `1` × 727，`NULL` × 1 |
| `garmin_activity` | nullable，无默认值 | `1` × 661，`NULL` × 1 |
| `xunji_train` | nullable，无默认值 | `1` × 131，`NULL` × 2 |
| `body_metric` | nullable，无默认值 | `1` × 2 |

四表均有 `user_id -> users.id` 外键约束。

**为何判定为良性、暂不清理**：

1. `user_id` **全部 nullable 且无默认值** —— 单用户代码插入新数据时该列为 `NULL`，
   而 SQLite 中 `NULL` 外键不触发约束检查，读写均正常；
2. 历史主数据（727 条 workout 等）已统一归属 `user_id=1`（admin），取值一致无歧义；
3. Alembic 的 7 个迁移文件**均不涉及**这些表与列，且 Alembic 只比对 `alembic_version`、
   不校验实际 schema —— 未来在 `main` 新增迁移**不会因此报错**；
4. 清理需重建 4 张表（其中 `garmin_activity` 独占 224 MB），在 486 MB 的库上属中高风险操作，
   而收益仅是"schema 看着干净"。

→ **结论：投入产出比不划算，暂不处理。** 若将来出现以下任一情况再重新评估：
需要在 `main` 上对这 4 张表做结构变更 / 恢复多用户开发 / 数据库出现相关报错。
